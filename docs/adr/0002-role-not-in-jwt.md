# 0002. JWT に role を含めず、DB から取得する

- 要約: JWT に role を含めず、認証のたびに DB から最新の role を取得する
- 状態: 採用
- 日付: 2026-11-12
- 関連: issue #164、PR #165、issue #205

## 背景

クライアントが管理者向けの操作を出し分けられるように、認証系 API
（register / login / me）のレスポンスに `role` を追加することになった（#164）。
このとき、JWT のペイロードにも `role` を入れるかを決める必要があった。

- トークンは有効期限 30 日の単一トークンで、失効させる仕組みはない。
- 認証ミドルウェアは、JWT の `id` から DB を引いて `role` を読んでいる。

## 検討した選択肢

| 案                              | 長所                                     | 短所                                           |
| ------------------------------- | ---------------------------------------- | ---------------------------------------------- |
| A. JWT に `role` を含める       | 認可のための DB 参照を省ける             | 権限を変えても、期限切れまで古い `role` が残る |
| B. JWT に含めず、毎回 DB を引く | 権限の変更が次のリクエストから反映される | 認証付きリクエストごとに DB 参照が必要         |

## 決定

**B** を採用する。JWT のペイロードは `id` / `username` / `email` に限定する。

## 理由

A では、権限を変更した後も古い値がトークンの有効期限（30 日）まで残る。

## 結果・トレードオフ

- 認可の判定は、常に DB の最新の値を使う。
- 認証付きリクエストごとに、ユーザーの DB 参照が発生する。
- クライアントが受け取る `role` は表示の出し分けにだけ使い、権限の判定はサーバーが行う。
- ペイロードに `role` が入らないことは、テストで確認している。
- 今後の課題: アクセストークンを短命化する場合（#205）も、この方針を保つかを確認する。
