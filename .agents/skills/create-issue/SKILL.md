# Issue 作成

## 方針

AI にも人にも作業しやすい Issue にするため、**作業の境界と完了条件**を明確にする。
「目的」「完了条件」「変更しないもの」は最低限書く（他は必要に応じて省略可）。
複数の目的がある場合は Issue を分ける。

## テンプレート

```markdown
## 背景
なぜ必要か。現在の問題や経緯。

## 目的
実装方法ではなく、利用者やシステムがどうなるか。

## 対応内容
具体的な作業範囲。対象ファイルが不明なら、既存実装を確認して最小限の変更とする旨を書く。

## 完了条件
- 画面・処理・テストなど、確認可能な形で箇条書きにする

## 変更しないもの
関係のないリファクタ・仕様変更を防ぐため、対象外を明記する。

## 確認方法
実行するコマンド（例: `cd server && npm run lint` / `check-types` / `test:ci`）や手動確認の手順。
```

## 手順

1. 依頼内容から、上記の項目を埋める。不足があれば、推測で補わずユーザーに質問する。
2. 仕様の根拠は `kadai.txt` や既存ドキュメントで確認する。存在しない API・機能を書かない。
3. タイトルは `[TYPE] 説明（日本語）`。
4. ラベルは既存のものから選ぶ（`bug` / `enhancement` / `documentation` / `chore` / `test` / `frontend` / `backend` など。`gh label list` で確認）。
5. **作成前に、タイトル・本文・ラベルをユーザーへ提示して確認を取る。**
6. 確認後、`gh issue create --title ... --body ... --label ...` で作成し、URL を報告する。

## 守ること

- 秘密情報・個人情報を書かない。
- 調査のみの Issue は、「変更しないもの」に「今回は調査のみで、実装は行わない」と書く。
